우리반 자리·점심은 학급에서 반복적으로 발생하는 자리 추첨, 점심 메뉴 전달, 식사 조 편성 업무를 웹으로 통합한 프로젝트다. 학생은 필요한 정보를 조회하고 신청하며, 관리자는 명단과 운영 규칙을 관리한다. 단순히 결과를 보여주는 데서 나아가 자리표 공개 시점, 신청 마감, 취소 후 재편성, 사용 불가 좌석처럼 실제 운영에서 발생하는 예외를 함께 처리하도록 구성했다.

## 📖 프로젝트 소개

### Background

학급 운영에는 반복되는 작은 업무가 많다. 자리를 바꿀 때는 학생 전원이 빠짐없이 배치되어야 하고, 사용할 수 없는 좌석을 제외해야 한다. 다음 자리표는 미리 준비하되 정해진 시점에 공개해야 한다. 점심시간에는 층별 메뉴를 확인하고, 함께 식사하고 싶은 학생의 신청을 받아 조를 나누는 과정도 필요하다.

이 업무들이 분리되어 있으면 학생은 정보를 여러 곳에서 확인해야 하고, 관리자는 신청 변경이나 자리 상태를 각각 반영해야 한다. 특히 신청 취소 후에도 기존 조에 이름이 남거나, 과거 자리표와 새 조 편성 결과가 섞이는 문제는 화면 표시만으로 해결하기 어렵다.

이 프로젝트는 이러한 운영 요구를 학생 화면과 관리자 화면으로 나누고, 데이터와 처리 규칙은 서버 및 데이터베이스에서 함께 관리하는 방향으로 구성했다.

### Solution

학생 화면에서는 자리표, 10층·20층 점심 메뉴, 밥친구 신청과 편성 결과, 자리 기준 조를 확인할 수 있다. 관리자 화면에서는 학생 명단, 자리표 예약, 좌석 상태, 신고 처리, 식단, 신청 마감과 조 편성을 관리한다.

시간에 따라 달라지는 공개·신청 규칙은 한국 시간을 기준으로 처리한다. 신청과 취소는 데이터베이스 함수에서 기존 조의 갱신과 함께 처리하고, 식단 수집은 한 층의 오류가 다른 층의 저장까지 막지 않도록 구성했다.

## ⚙️ 핵심 기능

### 01. 무작위 자리 배치와 예약 공개

- **기능 설명:** 관리자가 자리표를 생성하거나 직접 배치한 뒤 적용일을 지정해 예약한다. 학생은 공개 시점에 맞는 자리표를 확인한다.
- **구현 방식:** 1~30번 좌석 중 사용 불가 좌석을 제외하고, 학생 명단과 사용 가능한 좌석을 각각 Fisher–Yates 방식으로 섞는다. 저장 시 학생 중복, 누락, 잘못된 자리 번호, 사용 불가 좌석 포함 여부를 검사한다.
- **공개 규칙:** 적용일 7일 전 한국 시간 00시부터 공개하며, 다음 자리표의 공개 시점까지 표시한다. 공개 가능한 예약이 없으면 빈 자리표를 보여준다.
- **의의:** 자리표를 미리 준비하면서도 공개 시점을 통제할 수 있고, 빈자리가 생기는 위치도 무작위 배치 대상에 포함한다.

### 02. 사용 불가 좌석과 자리 오류 신고

- **기능 설명:** 관리자가 좌석별 사용 불가 여부와 사유를 등록하고, 학생은 자리 번호와 사유를 입력해 오류를 신고한다.
- **구현 방식:** 좌석 상태와 신고를 데이터베이스에 저장한다. 학생과 관리자 화면은 공통 좌석 상태를 조회하며, 관리자는 신고를 확인하고 처리 완료로 변경한다.
- **예외 처리:** 기존 자리표의 좌석이 이후 사용 불가로 바뀌면 배치된 이름과 사용 불가 사유를 함께 표시한다. 새로운 자리표를 저장할 때는 사용 불가 좌석을 검증한다.
- **의의:** 브라우저별 임시 설정에 의존하지 않고 모든 사용자가 같은 좌석 상태를 확인할 수 있다. 신고자의 이름과 신고 사유는 학생 조회 API에 공개하지 않는다.

### 03. 10층·20층 점심 메뉴 자동 수집

- **기능 설명:** 학생은 날짜에 맞는 층별 메뉴를 확인하고, 관리자는 자동 수집과 수동 등록을 사용할 수 있다.
- **구현 방식:** 10층은 GitHub의 식단 데이터를, 20층은 Welplan MCP의 `get_restaurant_menu`를 조회한다. 20층은 멀티캠퍼스 식당의 요청 날짜 점심 중 식당 내 식사 메뉴를 추출한다.
- **장애 대응:** 외부 요청에 5초 제한을 적용하고, 두 층은 `Promise.allSettled`로 병렬 수집한다. 한 층만 실패하면 성공한 층의 결과를 저장하고 실패 내용을 반환한다.
- **자동화:** Vercel Cron 설정에는 평일 한국 시간 오전 9시 메뉴 수집이 등록되어 있다.
- **의의:** 층별 정보를 한 화면에 모으면서 외부 데이터 제공처의 일시적인 오류가 전체 수집 실패로 이어지는 범위를 줄인다.

### 04. 신청 기반 밥친구 편성

- **기능 설명:** 학생이 10층 또는 20층 밥친구를 신청하고, 마감 전까지 변경하거나 취소한다. 관리자는 날짜별 신청 현황과 조 편성을 관리한다.
- **구현 방식:** 같은 층의 활성 신청자만 대상으로 기본 3~4명 조를 생성한다. 같은 층 신청자가 정확히 5명이면 5명 조 하나를 만들며, 1~2명이면 조를 생성하지 않는다.
- **정합성 처리:** 마감 전에 이미 조가 생성된 상태에서 신청이 바뀌거나 취소되면, 신청 변경과 조 갱신을 하나의 데이터베이스 트랜잭션에서 처리한다.
- **마감 관리:** 기본 마감은 한국 시간 12:00이며 관리자가 시·분 단위로 변경할 수 있다. 화면과 서버, 데이터베이스에서 마감 규칙을 적용한다.
- **정보 공개:** 학생에게는 층별 신청 인원과 편성된 조의 멤버를 제공한다. 신청자 전체 명단은 관리자 영역에서 관리한다.
- **자동화:** Supabase Cron이 매분 마감 여부를 확인해 평일 자동 편성을 수행한다. Vercel의 정오 작업은 보조 실행으로 구성되어 있다.

### 05. 현재 자리 기준 조 편성

- **기능 설명:** 관리자가 최소·최대 인원을 지정하면 현재 적용 중인 자리표를 기준으로 가까운 학생끼리 조를 만든다. 학생은 생성된 결과를 조회한다.
- **구현 방식:** 교실 통로를 반영한 좌표로 좌석 간 맨해튼 거리를 계산한다. 여러 시작점에서 가까운 학생을 모으고, 조 사이의 구성원을 교환하며 점수를 개선한다.
- **판단 기준:** 조 안에서 가장 멀리 떨어진 구성원 사이의 거리를 우선 줄이고, 전체 구성원 쌍의 거리 합도 함께 고려한다. 전역 최적해를 보장하는 방식은 아니다.
- **검증:** 최소 2명, 최대 10명 범위에서 설정을 받고, 전체 학생을 요청 범위의 조로 빠짐없이 나눌 수 없으면 오류로 안내한다.
- **의의:** 무작위 식사 조와 별도로, 현재 교실에서 가까이 앉은 학생끼리 활동할 수 있는 편성 기능을 제공한다.

### 06. 학생 명단과 관리자 운영

- **기능 설명:** 관리자가 학생 추가, 이름·메모 수정, 활성 상태 변경, 삭제를 수행한다.
- **구현 방식:** 활성 학생 명단을 자리 배치와 밥친구 처리의 기준으로 사용한다. 관리자 작업은 인증된 서버 API를 통해 수행한다.
- **인증 방식:** 서버 환경 변수로 관리자 계정을 관리하고, HMAC 서명과 만료 시간이 포함된 세션을 발급한다. 쿠키에는 `HttpOnly`, `Secure`, `SameSite=Strict` 속성을 적용한다.
- **의의:** 명단과 운영 기능을 관리자 화면에서 관리하고, 서버 전용 Supabase 키는 서버 환경 변수에서 사용한다.

## 🏗️ Architecture

### Processing Flow

```text
학생 화면 (index.html)
  ├─ Supabase 조회 / 공개 RPC
  │    └─ 활성 학생, 식단, 공개 가능한 자리표
  └─ Vercel Functions
       ├─ /api/seats               좌석 상태 조회·오류 신고
       ├─ /api/meal-friends        신청 현황·신청·취소·조 조회
       └─ /api/proximity-groups    자리 기준 조 조회

관리자 화면 (admin.html)
  └─ 인증된 Vercel Functions
       ├─ /api/admin              학생·자리·신고·마감·조 관리
       └─ /api/fetch-welplan-menu  식단 수동 수집 실행

자동 작업
  ├─ Vercel Cron → 층별 식단 수집 → daily_menus 저장
  ├─ Supabase Cron → 마감 확인 → 밥친구 자동 편성
  └─ Vercel Cron → 밥친구 보조 편성 실행

Supabase / PostgreSQL
  ├─ 운영 데이터 저장
  ├─ 신청·취소와 조 갱신의 트랜잭션 처리
  ├─ 자리표 공개 시점 및 데이터 유효성 검사
  └─ 테이블·함수 접근 권한 관리
```

## 👨‍💻 담당 역할

> 다음은 코드에서 확인되는 구현 영역이다. 개인별 작업 이력은 확인되지 않았으므로, 개인 포트폴리오로 사용할 때 실제 담당한 항목을 선택하고 기여 범위를 보완해야 한다.

### 01. 학생·관리자 화면과 학급 운영 흐름

학생용 정보 조회·신청 화면과 관리자용 운영 화면을 구성한 영역이다. 자리표 공개, 식단 확인, 신청 마감과 취소, 신고 처리처럼 사용자가 수행하는 작업을 화면과 API로 연결한다.

**Tech:** HTML, CSS, JavaScript, Fetch API

### 02. 서버 API와 데이터 정합성

관리자 인증, 요청 검증, Supabase 연동을 구성한 영역이다. 신청·취소와 조 갱신은 데이터베이스 함수로 묶고, 공개 데이터와 관리자 전용 데이터의 접근 범위를 나눈다.

**Tech:** Node.js, Vercel Functions, Supabase, PostgreSQL, HMAC 세션

### 03. 편성 알고리즘과 외부 데이터 자동화

자리 추첨, 좌석 거리 기반 조 편성, 층별 메뉴 수집과 예약 실행을 구성한 영역이다. 외부 요청 시간 제한, 부분 실패 저장, 마감 후 중복 실행 방지 같은 운영 예외를 처리한다.

**Tech:** Fisher–Yates, 맨해튼 거리, 탐욕적 구성·구성원 교환, MCP, Cron

## 🔥 문제 해결

> 아래 내용은 현재 코드와 변경 문서에 근거해 재구성한 설계상의 문제 해결이다. 운영 장애 발생 횟수나 실제 개선 수치는 별도로 측정되지 않았다.

### 01. 신청 취소 후 기존 조에 학생이 남는 문제

**Problem**

신청 데이터만 삭제하면 이미 만들어진 조에는 취소한 학생의 이름이 남을 수 있다. 학생 화면과 실제 신청 상태가 달라지는 문제다.

**Cause**

신청 상태와 편성 결과가 서로 다른 데이터로 저장되므로, 각각 갱신하면 한쪽만 반영되는 상황이 생길 수 있다.

**Solution**

`submit_meal_friend`에서 마감 시간을 검증하고 신청 변경·취소와 기존 조 갱신을 하나의 트랜잭션으로 처리한다. 변경된 인원에 맞춰 층별 조를 다시 편성한다.

**Result**

5명 조에서 한 명이 취소하면 남은 4명으로 재편성하고, 1~2명만 남으면 해당 층의 조를 생성하지 않는 규칙을 구현했다. 기존 자동 테스트에도 취소 후 조 갱신을 검증하는 사례가 포함되어 있다.

### 02. 한 층의 식단 수집 오류가 전체 조회를 막는 문제

**Problem**

10층과 20층은 데이터 제공처가 다르다. 한쪽이 느리거나 오류를 반환할 때 정상적인 다른 층의 데이터까지 저장하지 못할 수 있다.

**Cause**

두 외부 요청을 하나의 성공 조건으로 취급하면 개별 장애가 전체 수집 실패로 확대된다.

**Solution**

요청마다 시간 제한을 적용하고, `Promise.allSettled`로 결과를 개별 처리한다. 성공한 층의 메뉴만 갱신하며 실패한 층의 오류는 경고로 남긴다. 두 층이 모두 실패했을 때 전체 요청을 실패 처리한다.

**Result**

한 층만 수집되어도 저장할 수 있는 흐름을 구성했다. 20층은 아침·저녁·포장 메뉴를 점심 식당 메뉴로 혼동하지 않도록 필터링하며, 날짜별 데이터와 수집 출처를 저장한다.

### 03. 자리표 사전 공개와 현재 자리 기반 조의 기준 충돌

**Problem**

학생에게는 다음 자리표를 미리 보여줘야 하지만, 자리 기준 조는 현재 실제로 적용 중인 자리표를 기준으로 만들어야 한다.

**Cause**

자리표의 공개일과 적용일은 서로 다른 의미다. 같은 조회 조건을 사용하면 사전 공개된 다음 자리표가 현재 활동 조의 기준으로 잘못 사용될 수 있다.

**Solution**

학생 자리표는 적용일 7일 전 공개 규칙으로 조회하고, 자리 기준 조는 오늘 이하의 적용일 중 가장 최근 자리표를 기준으로 처리한다. 저장된 조가 기준 자리표의 적용일과 맞는지도 확인한다. 관련 SQL에는 자리표 변경에 따라 저장된 조를 무효화하는 트리거가 정의되어 있다.

**Result**

사전 공개용 자리표와 현재 활동용 조의 기준을 분리했다. 현재 기준에 맞는 조가 없으면 새 편성이 필요하다는 상태를 제공한다.

### 04. 변경 가능한 마감 시간과 자동 작업 중복 실행

**Problem**

관리자가 마감 시간을 바꿀 수 있는 환경에서 고정된 시각의 예약 작업만 사용하면 실제 마감 전에 편성되거나 마감 이후 실행이 늦어질 수 있다. 여러 자동 작업이 같은 날 중복 실행될 가능성도 있다.

**Solution**

Supabase Cron이 매분 설정된 마감 시간을 확인하고, 평일과 실행 이력을 검사해 편성한다. Vercel의 정오 작업도 같은 데이터베이스 함수를 사용해 실행 조건을 확인한다. 마감 시간을 실제로 변경하면 당일 자동 편성을 다시 수행할 수 있도록 실행 상태를 갱신한다.

**Result**

운영 설정과 자동 편성의 판단 기준을 데이터베이스 함수로 모았다. 기존 테스트에는 마감 직전·정각, 주말 제외, 중복 실행 방지, 마감 시간 변경 사례가 포함되어 있다.

## 💡 회고

### What I Learned

**운영 규칙은 화면 밖에서도 일관되게 적용해야 한다.** 마감 후 버튼을 비활성화하는 것만으로는 직접 요청을 막을 수 없다. 서버와 데이터베이스에서도 시간을 검증하고, 관련 데이터 변경을 하나의 작업으로 묶어야 신청 상태와 편성 결과를 맞출 수 있다.

**공개일과 적용일처럼 비슷해 보이는 시간도 의미를 나눠야 한다.** 다음 자리표를 미리 보여주는 요구와 현재 자리로 조를 만드는 요구는 서로 다른 기준을 사용한다. 날짜의 의미를 데이터 조회 조건에 정확히 반영하는 것이 중요하다.

**외부 연동은 실패했을 때의 동작까지 설계해야 한다.** 메뉴 제공처마다 응답 형식과 상태가 다르므로, 정상 응답 파싱뿐 아니라 시간 제한, 부분 성공, 오류 표시, 수동 등록 경로가 함께 필요하다.

**기능이 늘수록 코드와 데이터베이스의 적용 상태를 함께 관리해야 한다.** 새 API를 배포해도 테이블이나 함수가 이전 상태라면 정상 동작하지 않는다. SQL 적용 순서와 재배포 절차도 서비스 운영의 일부로 다뤄야 한다.
